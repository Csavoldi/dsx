# T16: a trellis format made for this CPU

Status as of October 24, 2026: T16 v1 is shipped and integrated into CPU decode, GPU decode and prefill. The default
package is one ~252 GB GGUF with IQ4_NL Engram; Q6_K is an alternative. The calib5 requant completed and scored
KL ~0.202 versus v1's 0.196 with the same output gains, so it did not replace v1. The gains were selected on the eval.
This document retains the earlier experiments and their original protocols; [current state](current-state.md) and
[FINDINGS §9b](../FINDINGS.md#9b-decode-small-kernels-launch-structure-and-the-dev-4-merge-2026-10-23) record later results.

T16 is a trellis expert format with shipped 1.5-, 2- and 2.5-bit variants. It aims at EXL3's accuracy while
decoding at RAM speed on an AVX2 + AVX-VNNI desktop CPU (i7-12700K). It is the same kind of format as EXL3 (QTIP's bitshift trellis); only the function that turns
a trellis state into a weight differs, and that function was picked for what this CPU executes cheaply.

Status: codebook, CPU decode, GPU decode and accuracy on real experts measured (this page); quantizer = exllamav3's own, patched.

## How a trellis format stores weights

- Weights are first rotated (128-wide Hadamard blocks), which makes them close to Gaussian.
- Each 16 x 16 tile of weights is stored as one bit stream. Weight *i* of the tile owns a **state**: the 16-bit window
  of the stream ending at bit 16 + K*i. Consecutive weights' windows overlap by 16 - K bits, so each weight costs only
  K new bits (K = 2 gives 2 bits per weight).
- A weight's value is a fixed function of its state: `w = f(state) * scale`. The function acts as a codebook of 65,536
  entries. Because neighbouring states overlap, the quantizer must pick the whole bit stream at once; it does so with
  the Viterbi algorithm over the 65,536 states (and LDLQ / GPTQ-style error feedback across columns, using each
  expert's input Hessian).
- Accuracy comes from the codebook being large and Gaussian-shaped. Speed comes from how cheaply f can be evaluated:
  there is no table, so f is computed for every weight.

## The two codebooks

| | EXL3 "mul1" | T16 |
|---|---|---|
| product | p = state x 0x83DCD12D mod 2^32 | p = state x 0x3A2F mod 2^16 |
| value | (sum of p's 4 bytes - 510) / 147.7 | (sum of p's 2 bytes - 255) / 104.51 |
| CPU multiply | `vpmulld`: 8 weights, 2 uops | `vpmullw`: 16 weights, 1 uop |
| dot product | `vpdpbusd` on the product's 4 bytes x activation (4x) | `vpdpbusd` on 2 bytes x activation (2x), 2 weights per dword |

The byte sum makes the dot product exact integer math: sum_w f(s_w) x_w = (sum over bytes of p_w x x_w - offset x
sum x_w) / norm, so dequantization and the activation product fuse into `vpdpbusd`.

## Accuracy of the codebook (Gaussian data, 2 bits/weight)

Viterbi-quantized i.i.d. Gaussian tiles, MSE / variance at the best scale (`bench/cbq.c`, `bench/cbsearch.c`):

| Codebook | MSE |
|---|---:|
| rate-distortion bound | 0.0625 |
| EXL3 mul1 | 0.0640 |
| i.i.d. Gaussian table (random codebook, reference) | 0.0641 |
| **T16 (0x3A2F, 2-byte sum)** | **0.0665** |
| T16 with other 16-bit constants | 0.0665-0.0672 (0xD12D: 0.0708) |
| 16-bit multiply, 4-byte sum of the 32-bit product | 0.0654 |
| four 16-entry tables on the state's nibbles (shuffle-only) | 0.076-0.079 (0.0671 on a scrambled state) |
| 2-bit scalar (Lloyd-Max) | 0.1175 |

T16's extra 4% MSE over mul1 is worth about 0.03 bits per weight. The multiplier constant matters (0xD12D is 11% worse).

## Decode cost on the i7-12700K

Single token, 6 experts per call (gate/up 2304 x 5120, down 5120 x 2304), a pool of 64 experts read from RAM
(`bench/trellis_floor.c`, `bench/exl3bench.py`). These kernels use a simplified layout (one bit stream per output row,
no Hadamard); exllamav3's real layout is measured further down.

| Kernel | One P-core | Whole CPU per call | Limit |
|---|---:|---:|---|
| exllamav3 AVX2 (EXL3 K2) | 12 G weights/s | 2.07 ms | vector ports 0/1 (+ maddubs/madd, spills) |
| mul1, minimal AVX-VNNI kernel, 4 rows at a time | 17.6 G weights/s | 1.51 ms | ports 0/1: srlv + 2 x pmulld + vpdpbusd per 8 weights |
| dsx today, Unsloth UD-IQ1_M experts | | 1.45 ms | table lookups + RAM |
| **T16, AVX-VNNI kernel** | **39 G weights/s** | **1.24 ms (43 GB/s)** | **RAM bandwidth** |

T16's inner loop per 64 weights: one 32-byte load, two `vpshufb` that build 16-bit windows from byte pairs, then per
weight class r = 0..3 one `(lo >> 2r) | (hi << 16-2r)`, one `vpmullw`, one `vpdpbusd`. Six of the eight P-cores
already saturate RAM.

## Decode cost on the RTX 3090

Single token, 6 experts, measured by DSX Dev 3 (`bench/t16_gemv.cu`, v5), each config in its own
process with pauses so the 230 W power cap does not throttle it. Same simplified row layout as above, no Hadamard:

| Kernel | gate/up x6 | down x6 |
|---|---:|---:|
| **T16 v5 (incl. its activation quantization)** | **33.8 us** | **35.9 us** |
| dsx IQ2_XXS tile (+2 us activation quantization) | 43 us | 39 us |
| dsx IQ1_S tile (+2 us) | 41-42 us | 40 us |
| plain read of the same bytes / DRAM floor at 936 GB/s | 22.5 / 19 us | |

Per 4 weights: 4 SHF (windows) + 4 IMAD (x 0x3A2F) + 4 PRMT (gather low and high bytes) + 2 dp4a; int8 activations
with a scale per 256 and per-word sums for the -255 offset. ncu: ALU pipe 70-75%, FMA pipe 53-57%, DRAM 63-66%.
Measurement note: dsx-serve.sh's 230 W cap throttles a 3090 within about a second of back-to-back GEMVs (44 -> 65 us in
one process), so long benchmark loops understate both formats; real decode bursts are short.

## exllamav3's real layout

What exllamav3 v1.6.4 (commit da68d57) writes, and what the T16 patch changes. Sources read:
`exllamav3/exllamav3_ext/quant/exl3_dq.cuh` (bit windows), `reconstruct.cu` (fragment order), `codebook.cuh`
(decode), `exllamav3/modules/quant/exl3.py` (forward, `get_weight_tensor`), `exllamav3/modules/quant/exl3_lib/quantize.py`
(`ldlq`, `tensor_core_perm`).

- **Tensors per matrix** `W` (in x out): `trellis` u16 [in/16][out/16][16 K] (K = 1.5 and 2.5 store 16 K + 8 / 16 K
  words per tile in the half-rate path), `suh` fp16 [in], `svh` fp16 [out], and the codebook marker (`mul1`, set to
  0x3A2F by the T16 patch). `suh`/`svh` are signs times per-channel scales (refit after quantization).
- **Forward**: `y = had128(had128(x * suh) @ W_inner) * svh`, Walsh-Hadamard over 128-wide blocks, normalized.
- **Tiles**: W_inner is 16 x 16 tiles in row-major tile order (`[k/16][n/16]`). Each tile is a circular bit stream of
  256 K bits, read through u32 words most-significant bit first (the u16 array viewed as u32). Position t's state is the
  16 bits ending at bit (t + 1) K, wrapping to the end of the tile for the first positions (`dq`, `dq8_*`).
  Half-integer K alternates K - 0.5 and K + 0.5 bits per position (`dq8_half`).
- **Position order**: position 8L + j (L = 0..31) is row (2q, 2q+1, 2q+8, 2q+9)[j % 4] (q = L % 4) and column
  L / 4 (+ 8 for j >= 4) of the tile (`tensor_core_perm`, `reconstruct.cu`). Lane L's 8 decoded values are exactly its
  two f16 B fragments of `mma.m16n8k16` for the tile's columns 0-7 and 8-15.
- **Value**: state s -> p = low 16 bits of s * 0x3A2F -> fp16 `fma(1024 + (p & 0xFF) + (p >> 8), 0x20e6, 0xca1e)`, i.e.
  about (lo + hi - 255) / 104.51 rounded to fp16: one of 511 fp16 values, so an exact reconstruct is a 511-entry table.
- **Quantizer constraint**: LDLQ quantizes 16 input rows at a time (`ldlq`: `rows = b_weight[bi:bj]`, cut into 16 x 16
  tiles, permuted with `tensor_core_perm`, encoded). Any grouping of 256 weights inside one 16-row band is compatible
  with LDLQ, e.g. 1 x 256 strips (one input row, 256 consecutive outputs).

## Decode cost in the real layout

K = 2, 6 experts per call drawn from a pool of 64 in RAM / a pool of copies >= 256 MB on the GPU, both Hadamards and
suh/svh included, checked against a scalar decode with exllamav3's indexing (`bench/trellis_tile.c`, `bench/t16_tile.cu`;
CPU: 0 of 64 outputs differ, GPU: max error 3e-6 of max |y| against the fp16 table, 2e-7 for the int8 kernel against
the same int8 activations). UD's mix: `cpubench ud=MODEL.gguf` (the model's own per-layer types) and
`nvidia/tests/gpu_expbench.rs`, measured in the same session, interleaved, one GPU config per process after a pause.

| 6 experts, single token | CPU, 14 threads | GPU gate/up x6 | GPU down x6 |
|---|---:|---:|---:|
| Unsloth UD-IQ1_M mix, dsx kernels | 1.72-1.75 ms | IQ2_XXS 43 + 2 us, IQ1_S 41-42 + 2 us | 39 + 2, 40 + 2 us |
| **T16, exllamav3 layout** | **1.69-1.75 ms** | **55.2 us** (f16 mma) / 57.8 us (int8 mma) | **54.4 us** / 56.5 us |
| T16, row layout (above, no Hadamard) | 1.24 ms | 33.8 us | 35.9 us |

- **CPU, tie.** Per 32 weights: one `vpshufb` builds 8 big-endian 24-bit windows (positions 4m + r end 2r bits past a
  byte), then per r one shift, one `vpmullw`, one `vpdpbusd` into one accumulator per tile position (positions keep
  their own sums over the k blocks of a tile column, folded into the 16 columns at the end; the -255 sum(x) term is the
  same for every output). Tiles are byte-swapped and stored column-major at load (same bytes). 0.66 instructions per
  weight (perf, P-cores), 31 GB/s of weights: partly compute-bound. The first version (scalar windows, `vpmulld`, tiles
  9 KB apart) took 3.2-3.6 ms; a staging buffer that failed store forwarding cost another 1.6x.
- **GPU, about 30% slower.** Both kernels decode a tile per warp straight into mma fragments; the GEMV is integer-bound
  (ncu: ~8 instructions per weight; f16 kernel: FMA-heavy pipe 68%, math-pipe throttle the top stall; int8 kernel: ALU
  62%, FMA-heavy 44%; DRAM 41-44%). The two Hadamard kernels add ~6 us. The row layout's kernel does the same decode at
  ~3.7 instructions per weight: there each lane walks one row's stream, so a 32-bit load serves 16 consecutive windows
  and the activation side is a plain dot product, where the tile layout needs a 64-bit funnel shift per 8 positions
  and per-tile index math.
- Not measured: K = 1.5 / 2.5 (half-rate path), which the planned quant uses for most matrices.

**Verdict.** On exllamav3's layout T16 ties UD on the CPU and is ~30% slower on the GPU, so decode would get slower
wherever GPU-resident experts dominate. A layout from our own quantizer avoids that: 1 x 256 strips along the output
dimension (one input row, 256 outputs) stay inside LDLQ's 16-row bands, so exllamav3's quantizer can emit them with a
change to the tile reshape and permutation. The Viterbi search still sees 256-weight sequences of near-Gaussian
weights after the Hadamard, so no quality change is expected (confirmed for column-major tiles on the layer 5 / 20
experts: "Tile order" below). Decode
would then cost about what the row-layout kernels above do.

## Decode cost model

Decode speed is the larger of the memory time and each execution pipe's instruction time. All numbers measured on .102
(`bench/gpu_isa.cu`: lanes per SM clock, one 1024-thread block per SM, clock64; `bench/cpu_isa.c`: per core clock,
calibrated with a dependent add chain).

RTX 3090 (82 SMs, ~1.74 GHz at 285 W, ~1.395 GHz under ncu), per SM per clock:

| Operation | Lanes / clk / SM | Pipe |
|---|---:|---|
| SHF (funnel shift), LOP3, PRMT | 64 | ALU |
| IMAD, IDP4A, HFMA2 | 64 | FMA-heavy |
| IADD3 | 64 | |
| FFMA | 128 | FMA |
| LDS 4 or 8 bytes, data-dependent index | 16 (bank conflicts + address math) | shared memory |
| LDS 16 bytes, data-dependent | 8 | shared memory |
| int8 mma m16n8k32 | 0.2 per clk (~820 MAC) | tensor |
| f16 mma m16n8k16, f32 accumulate | 0.1 per clk (~205 MAC) | tensor |

i7-12700K, per core clock: P-core (4.8-4.9 GHz) vpshufb 2, vpsrlvd / vpsrld 2, vpmullw 1.6, vpdpbusd 1.6, vpmaddubsw 1.6,
vpmulld 0.74, vpaddd / vpand 3, vpermd 1, 32-byte load ~2, vpgatherdd (8 dwords) 0.17. E-core (3.7 GHz) vpshufb 0.5,
vpsrlvd 1.55, vpmullw 0.5, vpdpbusd 0.5, vpgatherdd 0.03: E-cores add little to this work.

**Budget.** GPU at ~850 GB/s: 3.4 T weights/s at K = 2 (4.5 T at K = 1.5, 2.7 T at K = 2.5), so each of the ALU and
FMA-heavy pipes may spend at most ~2.2 ops per weight at K = 2 (1.6 at K = 1.5, 2.7 at K = 2.5) before decode, not
memory, sets the time. CPU at 43 GB/s with 8 P-cores: ~4.5 weights per core clock at K = 2 (6 at K = 1.5). A
data-dependent table lookup costs 4 ALU ops' worth of throughput on the GPU (16 vs 64 lanes per clock) and a gather
yields ~1.4 entries per clock on a P-core, so a lookup-based code only pays if one lookup yields >= 4 weights.

**T16's floor** per weight: one window cut (shift), one product (IMAD / vpmullw), and the dot product. On the GPU, two
consecutive rows' products packed as [lo0 hi0 lo1 hi1] by one PRMT and dp4a'd with [x_k x_k x_k+1 x_k+1] give
x_k (lo0 + hi0) + x_k+1 (lo1 + hi1): 1.5 ALU + 1.5 FMA-heavy ops per weight, under the K = 2 budget.

**Validation (GPU, 6 experts, gate x6, K = 2).** SASS of the hot loops, per weight:

| Kernel | ALU ops | FMA-heavy ops | GEMV time | Limit |
|---|---:|---:|---:|---|
| v3: column-major tiles, lo/hi gather, per-tile 64-bit addressing | 2.85 | 1.6 | 39.4 us (ncu clock) | ALU (75% busy) |
| **v4: pair-packed dp4a, running pointer, one 16-byte x load per 8 rows** | **1.66** | **1.72** | **29.5 us** | load latency (long scoreboard), DRAM 60% |
| dsx IQ2_XXS tile (dsx-ud today) | | | 43 us (+2 us activation quant) | |

GEMV kernels alone, nsys medians at 285 W, interleaved in one session, two rounds (agreeing within 0.3 us), us:

| 6 experts | gate x6 | down x6 |
|---|---:|---:|
| dsx IQ2_XXS tile | 42.5-42.7 | 39.1-39.3 |
| dsx IQ1_S tile | 41.0 | 39.5 |
| dsx IQ2_XS tile | 50.2-50.4 | 42.7 |
| dsx IQ2_S tile | 51.7-51.8 | 49.2-49.3 |
| **T16 v4, K = 1.5** | **29.3** | **27.9** |
| **T16 v4, K = 2** | **29.5** | **27.9** |

(25.5 / 25.2 at K = 1.5 with tiles stored pair-major.) The IQ tiles add ~2 us of activation quantization per call; T16
adds 2.4 us activation prep (had128 + int8) and ~3.6 us output had128 * svh, which dsx would fold into its existing
activation-quantize and combine kernels. T16 v4 is faster than every IQ format of UD's mix at every K measured.

**CPU.** v3 (K = 2, byte-class windows: 0.66 instructions per weight by perf) ties UD's mix at 1.75 vs 1.73 ms per
6-expert call. v5 (any K, one tile column per lane) is exact but 2.6 ms: its window math is the modelled 4 port-0/1
ops per 8 weights, and building each column's 64-bit view lane by lane (scalar moves and inserts, from the assembly)
costs as much again. v6 builds them from byte-aligned loads instead (the views end at byte 3c + 3, 4c + 4, 5c + 5;
with tile words byte-swapped once at load a tile is its big-endian stream, so one or two 16-byte loads and a vpshufb
per 4 columns, masks fixed per K): 14 threads, interleaved with UD's mix (1.73 ms):

| CPU, 6 experts | ms per call | weight GB/s |
|---|---:|---:|
| UD-IQ1_M mix, dsx kernels | 1.73 | 28.6 |
| T16 v6, K = 1.5 | 1.55 | 25.7 |
| T16 v6, K = 2 | 1.57 | 33.7 |
| T16 v6, K = 2.5 | 1.78 | 37.1 (near RAM) |

K = 1.5 / 2 run at ~3.6 weights per P-core clock (model: 4), K = 2.5 is memory-bound.

**Verdict on speed.** With column-major position order inside exllamav3's tiles (in its quantizer only
`tensor_core_perm` changes) and kernels built from this budget, T16 decodes faster than UD's IQ mix on the GPU at every
K measured and on the CPU at K = 1.5 and 2 (K = 2.5 within 3%, memory-bound). The planned mix (gate/up 1.5 and down 2 in
layers 0-19, gate/up 2 and down 2.5 in 20-39) lands at or below UD on both.

## Accuracy on real experts

Every 8th expert of layers 5 and 20, quantized by exllamav3 with each expert's own Hessian from our calibration text,
scored as relative output error on calibration tokens and on Lucebox eval tokens (`quant/t16/real-experts-2026-10-21.txt`):

| Variant | bpw | L5 calib | L5 eval | L20 calib | L20 eval |
|---|---:|---:|---:|---:|---:|
| EXL3 mul1, K = 2 | 2.00 | 0.049 | 0.102 | 0.119 | 0.185 |
| T16, K = 2 | 2.00 | 0.051 | 0.106 | 0.123 | 0.194 |
| T16, K = 2,2,3 | 2.33 | 0.026 | 0.056 | 0.076 | 0.120 |
| Unsloth UD-IQ1_M's experts | 1.73 / 2.23 | 0.153 | 0.174 | 0.148 | 0.151 |

T16 stays within about 4% of mul1. Both trellis formats lose 1.6-2.4x going from calibration to eval tokens, while
Unsloth's experts lose 1.0-1.2x: the full-Hessian error feedback fits each expert's few thousand calibration tokens.
At equal bits on eval tokens the trellis formats are roughly tied with Unsloth's experts. How the Hessian is used
(diagonal only, damped, or none) is being tested next.

**Tile order.** Column-major position order inside each tile (position t = row t % 16, column t // 16), which the fast
kernels above need, against exllamav3's tensor-core order: same build and settings (damp 2, i.e. sigma_reg 2), only
`tensor_core_perm` swapped (`quant/t16/tile_order_eval.py`). Every 8th expert of layers 5 and 20 (12 each),
E = sum of err / sum of |y|^2 over the experts:

| Layer, K (gate/up/down) | Tokens | Tensor-core order | Column-major | Ratio | Per expert |
|---|---|---:|---:|---:|---|
| 5, 1.5/1.5/2 | calib | 0.07943 | 0.07966 | 1.003 | 0.98-1.01 |
| 5, 1.5/1.5/2 | eval | 0.12765 | 0.13111 | 1.027 | median 1.005, 0.93-1.04 |
| 20, 2/2/2.5 | calib | 0.06726 | 0.06719 | 0.999 | 0.99-1.01 |
| 20, 2/2/2.5 | eval | 0.09808 | 0.09678 | 0.987 | median 1.000, 0.94-1.09 |

Gaussian tiles: 0.07122 vs 0.07124. Calibration error agrees within 0.3%. The eval ratios go +2.7% in one layer and
-1.3% in the other, with per-expert medians at 1.00, so that spread is how much individual experts generalize
differently, not an effect of the order. Column-major tiles cost no quality.

## Making a T16 quant

`quant/t16/make_mul16_exllamav3.sh SRC DST` copies an exllamav3 v1.6.4 checkout and turns its mul1 slot into T16
(multiplier, a 16-bit mask before the byte sum, normalization constants k_inv = fp16 0x20e6, k_bias = fp16 0xca1e).
exllamav3's quantizer then emits T16 trellises: same Viterbi, same LDLQ, same Hadamard processing. Only the quantize
and reconstruct paths of the patched build are meant to be used; its inference kernels still say mul1.

**Time.** quantize_exl3 per expert (gate + up + down, 2304 x 5120 each), with the Hessians already on the GPU: 16.3 s at
K = 1.5/1.5/2 (RTX 3090 at 250 W) and 7.5 s at 2/2/2.5 (6.7 s on the other 3090 at 280 W). With the planned mix, all
40 x 384 routed experts take about 50 GPU-hours, ~25 h on .102's two GPUs, before Hessian collection and I/O.

The time goes to the fractional-K Viterbi kernel. exllamav3's tile quantizer on one matrix of Gaussian tiles (46,080
tiles, 250 W, `quant/t16/frac_k_time.py`) takes 1.4 s at K = 2 (integer kernel), 2.5 s at K = 2.5 and 5.0 s at K = 1.5 (`quantize_tiles_frac`).
Changing the batch from 128 to 256 or 512 tiles gives the same indices in 5.2 / 4.7 s. At K = 1.5 the fractional
kernel is about two-thirds of each expert's time, and the K = 1.5 layers are about 70% of a full quant, so a faster
fractional kernel would shorten a full quant the most.

## Other formats against the cost model

Research summary (October 2026): GSQ, SLQ, RCO, QTIP, EXL3, YAQA, Q-Palette, QuIP#, AQLM / PV-Tuning, VPTQ, GPTVQ,
HIGGS / FLUTE, ik_llama.cpp's KT types, CCQ, lattice codes (LLVQ, GLVQ), llama.cpp IQ types and Unsloth UD.

**Quality per bit.** Mean squared error on Gaussian data at 2 bits per weight, where the rate-distortion bound is 0.0625:

| Code | Gaussian MSE | Source |
|---|---:|---|
| Trellis: QTIP 1MAD / 3INST / HYB, EXL3 mul1, Q-Palette TCQ | 0.068-0.071 | [QTIP Table 1](https://arxiv.org/html/2406.11235v4), simulation |
| T16 | 0.071 | above |
| Leech lattice (LLVQ) | 0.078 | [2603.11021](https://arxiv.org/html/2603.11021v2) |
| E8 lattice (QuIP# E8P; IQ2_XXS uses an E8-derived grid) | 0.089 | QTIP Table 1 |
| 2-D VQ (HIGGS, Q-Palette VQ) | 0.107-0.109 | Q-Palette code, simulation |
| Scalar 2-bit grids (GSQ's {-2,-1,0,1}, ParetoQ) | 0.119-0.149 | simulation |

The trellis codes sit 9-14% above the bound, and no format found does better at 2 bits. A different codebook can
therefore gain at most about 12% in MSE over T16, roughly 0.1 bit.

**Decode cost.** The budget is ~2.2 ops per weight per pipe at K = 2, and T16 v4 spends 1.66 ALU + 1.72 FMA-heavy.

- Lookup codes (E8P, the IQ types, ik_llama.cpp's IQ2_KT at 4-5 ops per weight) are over budget. dsx's IQ2_XXS tile
  measures 42.5 us against T16's 29.5 us.
- Per-layer tables of 1 MiB (AQLM 1x16, VPTQ) do not fit hundreds of small expert matrices.
- Scalar grids decode in ~0.5-1 op per weight and could reach the DRAM floor (~21 us for gate x6 at K = 2, about 30%
  under T16 v4). They cost 1.7-2.1x T16's error at the same bits, though. GSQ makes up for that with Gumbel-softmax
  training (Kimi-K2.5 took 24 h on 8 x H200, [2604.18556](https://arxiv.org/html/2604.18556v2)), which is outside a
  $0 budget.
- exllamav3's own int8 GEMV for mul1 (one IMUL and one dp4a per weight) is the closest published kernel to T16 v4. Its
  comments measure it 29% faster than exllamav3's fp16 GEMV at K = 2 on a 3090
  ([exl3_gemv_int8.cu](https://github.com/turboderp-org/exllamav3/blob/da68d57de61781e5b74ad68698ac4caf36408d7a/exllamav3/exllamav3_ext/quant/exl3_gemv_int8.cu#L41-L50)).

**Where quality can still improve.** The format stays T16. The gains left are in how the quantizer uses data:

- **Rounding.** YAQA replaces LDLQ's input Hessian with Kronecker factors of the full-model KL and reports about 30%
  lower KL at 2 bits on Llama-3.1-70B-Instruct (0.497 -> 0.335, [2505.22988](https://arxiv.org/html/2505.22988v3)).
  For 40 x 384 experts its fp32 factors would take several TB, and exllamav3's collector skips fused MoE experts.
- **Bit allocation.** RCO (an exact-budget allocator from the GSQ group) and Q-Palette's ILP choose a bit width per
  tensor. dsx v2's tier selection by output error per byte already did this for UD types (KL 0.462 -> 0.395).
- **Calibration coverage.** Our trellis experts lose 1.6-2.4x from calibration to eval tokens, while UD's experts lose
  1.0-1.2x (Accuracy on real experts). This transfer gap is larger than any codebook difference above.

SLQ and RCO are allocators over INT2-INT8 rather than sub-3-bit formats. "RSO" matched no published method; RCO and
RSQ (a GPTQ token-weighting variant) are the nearest names.

## Completed work and remaining validation

The tile layout, GGUF types, loader, CPU/GPU kernels and one-file package are implemented. Damping, output-gain
correction and two full-model calibration runs were measured after the early layer tests above. The outstanding
